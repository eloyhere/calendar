# UI 架构设计文档

本文件是 `calendar` 应用中**界面层**的唯一约定来源。与 `docs/design.md`（数据分层契约）、
`docs/research.md`（深度研究页的设计依据）的分工是：

| 文件                 | 管什么                                                     |
| -------------------- | ---------------------------------------------------------- |
| `docs/design.md`     | 表、字段、换算；`UI -> entity -> store -> service -> repository -> sql -> sqlite` |
| `docs/research.md`   | **深度研究这一页**为什么长成这样（教育 / 心理 / UI 三条依据） |
| `docs/ui-architecture.md`（本文件） | **整个界面的骨架**：路由、主页面、主菜单、页面层次、跨页导航 |

三份文件都不允许"先改代码再补文档"。改路由、改菜单、改页面层次之前，先改本文件。

---

## 0. 结论摘要

被改动最大的一件事是：**把"智能体"从一个业务域提升为贯穿全应用的常驻助手，同时把它自己的五个
对话模式从主菜单里收进对话内部。**

改动前后的菜单对比：

| 维度             | 现状（`src/plugin/router.ts`）           | 本文件的设计                                              |
| ---------------- | --------------------------------------- | --------------------------------------------------------- |
| 主菜单形态       | 一条横向页头菜单，`ellipsis: false`      | 左侧常驻侧栏（分区 + 可折叠），页头只留品牌、面包屑、助手、窗口按钮 |
| 主菜单最大深度   | 3 层（历法 → 天文历 → 简介 / 日历 / 数据） | **2 层**（分组 → 页），三级结构改由页内切换器承担           |
| 一级项数量       | 6（概览 / 智能体 / 历法 / 命理 / 年 / 性能） | 3 个**分区**、**9 项一级**、共 26 项菜单条目                |
| 历法的 8 个实体  | 24 条路由、24 个页面文件、菜单里 8×3 项   | **1 条参数化路由**（`/calendar/:system/:view?`）+ **3 个页面文件**；菜单里 4 项 + 5 项二级 |
| 智能体对话       | 主菜单 5 项（新建 / 深度研究 / 数据调研 / 思维碰撞 / 课题研究） | 主菜单 1 项（对话）；其中**四个模式进对话内部的模式切换器**，思维碰撞并入助手抽屉 |
| 助手可达性       | 必须先离开当前页、进"智能体"域           | 任意页面 `Ctrl+/`（或侧栏/顶栏的「助手」），以**抽屉**形式就地打开——**不是 `Ctrl+K`**（那个留给命令面板） |
| 工作流           | 1 条路由、1 个空壳页（`PageShell` 占位） | 3 个页面（定义库 / 编排器 / 运行记录）+ 图编辑器            |
| 报告产物         | 散在会话里，没有入口                     | 独立的「报告」库（`/agent/report`）                        |

保留不动的部分：`docs/design.md` 的六层数据链路、`entity -> store -> service -> repository` 的
命名约定、"路由表即唯一配置"这条原则（菜单仍由路由表推导）、22 个分库与 `calendar.xlsx` 的对应关系。

## 1. 事实基础

本文件的所有结论都建立在这一节上。凡是本节没有的数据，正文一律不引用。

### 1.1 `calendar.xlsx`（实测）

用 `openpyxl` 以 `read_only` 打开逐表核对，结果如下（探针脚本见 `.temporary/probe_xlsx2.py`，
原始输出见 `.temporary/xlsx-facts.txt`）：

| 项       | 实测值                                                                     |
| -------- | -------------------------------------------------------------------------- |
| 文件体积 | 37,702,590 字节（约 36 MB）                                                 |
| 工作表数 | **24**                                                                      |
| 表名     | `前10 前9 前8 前7 前6 前5 前4 前3 前2 前1 第1 … 第13 第14`                    |
| 覆盖范围 | `-9999` … `13001`（每表 1000 年一块；`第14` 截断在 6186 行）                 |
| 列数     | 15（A 列全空；B…O 共 14 列有内容）                                          |
| 行数     | 每表 12370 或 12371；`第14` 为 6186                                          |
| 列 B     | 纪年块标签（`-9999`、`0001`、`2001`…），非空即"新年块开始"                   |
| 列 C     | 月名，形如 `正月大` / `闰四月小`（`大` = 30 天、`小` = 29 天）                |
| 列 D–G   | 朔月 / 上弦 / 望月 / 下弦四个时刻，始终齐全                                   |
| 列 H–M   | 主节气 / 主中气 / 副节中气两列一组（名称 + 时刻），部分行为空                 |
| 列 N     | 积月（块内序号，1,2,3…）                                                     |
| 列 O     | 月末积日                                                                     |
| 时间基准 | 天文纪年 **proleptic 格里高利历**，含 0 年与负数年                            |

**对界面的直接含义**：这是 24 × 1.2 万行 ≈ **29 万个朔望月**的历表，且它天然按"1000 年一块"
分片。任何"把历表铺成一张表"的设计都不成立，界面必须提供**块 → 年 → 月 → 相位**四级钻取。

### 1.2 实体与分库（取自 `docs/design.md` §3，与 `src/view/OverviewView.vue` 的清单一致）

22 个分库、合计 11,906,768 行。按界面上的**可达性**分成三类：

| 类别           | 分库                                                                       | 界面落点                                     |
| -------------- | -------------------------------------------------------------------------- | -------------------------------------------- |
| **有独立历法语义** | `synodic`（314,154）、`gregory`、`jupiter`、`natural`、`tree`、`tropical`、`astronomy`（后六个为 0 行，换算法则待实现） | 历法工作区；八套系统共用一套"简介 / 日历 / 数据" |
| **表类（非历法）** | `chronology`（0 行）、`climate`（1,743,926）、`phenology`（564,000）、`phase`（1,162,616） | 年表域；节气、月相作为**时间线上的事件层**    |
| **支撑层**     | `temporal`（6,943,509）、`part`（871,962）、`week`（1,453,271）、`primary`、`encounter`、`perform`、`epoch`、`dynasty`、`era`、`person`、`event` | 不作为独立页面，而是**历法 / 年表 / 命理三处的共用查询底座** |

这张表推翻了一个隐含假设：**22 个分库不等于 22 个页面**。真正需要独立页面的是"用户会主动去
找的东西"，而 `primary`（3 行）、`encounter`（28 行）、`perform`（808 行）这类只有几十到几百行
的表，独立成页只会得到一张一眼看完的空表——它们应当作为**历法详情里的附属面板**出现。

### 1.4 现状外壳与既定约束（不改的部分）

以下五条是**实测得出的结论**，本文件的方案必须与它们相容，不得回退：

1. **外壳挂 `/`、概览是它的空路径子页**。另外两种写法都实测失败（别名会与兄弟路由争抢匹配；
   `/` 纯 redirect 会让外壳同时需要 `component` 与 `redirect`，而后者类型是 `never`）。
2. **滚动只发生在页面内部**，窗口本身永不出现滚动条（`AppShell` 的 `ElMain` 是弹性宿主，
   `overflow: hidden`）。页面用 `flex: 1` 而非 `height: 100%` 撑满——弹性分配来的高度是
   `auto`，百分比高度解析不出确定值（实测 3897px，输入框被顶到屏幕外）。
3. **菜单高亮不能取 `route.matched[0].path`**（那永远是 `/`），必须取 `route.path`
   或本文件引入的 `meta.domain`。
4. **无边框窗口**：`AppHeader` 就是自绘标题栏，拖拽区按"整条可拖、只把真正可点的元素抠成
   `no-drag`"标注。窗口按钮固定在页头最右。
5. **懒加载必须是静态字面量**：`() => import("../view/...")`，动态模板串在构建期解析不出 chunk。

### 1.5 可用组件（`src/globals.d.ts` 实读）

已登记可直接在模板里用的 Element Plus 组件里，与本设计直接相关的有：
`ElSegmented`（模式切换器）、`ElTree`（历法体系树）、`ElSplitter` / `ElSplitterPanel`（三栏分隔）、
`ElDrawer`（助手抽屉）、`ElDialog`（命令面板与确认）、`ElTimeline`（年表时间线）、
`ElCascader`、`ElProgress`、`ElResult`、`ElBadge`、`ElAffix`、`ElWatermark`。

> 本文件的方案**不新增第三方依赖**。图编辑器用 SVG + 自绘节点实现，理由是节点数量上限为 64
> （`WORKFLOW_STEPS_MAX`），这个规模不需要图布局引擎；引入 `@vue-flow/core` 会让
> "第三方依赖只从 `src/plugin/` 进"这条约定多一个需要维护的转发层。

### 2.1 需求设计：导航该按什么切

**这是本次架构改动最重要的理论依据。**

| # | 依据 | 对本架构的要求 | 落点 |
| - | ---- | -------------- | ---- |
| 1 | **限界上下文（Bounded Context）**：DDD 把大模型拆成多个上下文并**明确它们之间的关系**；Evans 的原话是"大系统的领域模型完全统一是不可行也不划算的"。同一词在不同上下文含义不同，要靠 context map 描述关系（[Fowler 2014](https://martinfowler.com/bliki/BoundedContext.html)，**[已核实]**） | **一级导航 = 限界上下文，而不是 = 22 个 `.sqlite` 文件。**先把分库按用户语义归并，再给每个上下文一套自己的术语，跨上下文的查询显式画出来 | §3 的六个分组；§4 的 `/calendar/:system` 与 `/chronology` 分界；§10 的词表 |
| 2 | **卡片分类（Card Sorting）**：参与者按自己认为合理的标准把带标签的卡片分组；建议 30–50 张卡避免疲劳，**定性**至少 15 人、**定量** 30–50 人；用于**建立** IA（[NN/g](https://www.nngroup.com/articles/card-sorting-definition/)，**[已核实]**） | 本文件的一级分组是**提案**。落地前应当用"22 个分库实体名 + 主要功能入口"做成 30–50 张卡跑一轮，用真实分组修正命名 | §3 的验收条款 |
| 3 | **树测试（Tree Testing）**：只有层级标签、没有视觉设计，让用户找资源；任务措辞**不得使用分类的准确标签**，否则泄露答案（[NN/g](https://www.nngroup.com/articles/tree-testing/)，**[已核实]**） | 路由树冻结之前，把它导成纯文本层级跑 10–15 个任务（"找到某年号的起止年份""查贞观三年的节气"），统计首次点击正确率 | §3 的验收条款 |
| 4 | **需求信息项**：ISO/IEC/IEEE 29148:2018 规定需求工程的**过程**、**产出物**与**产出物的必备内容**（2018-11 第 2 版，92 页，2024-05 复审有效）（[ISO](https://www.iso.org/standard/72089.html)，**[已核实]**） | 本文档的每条架构条目都要**可验证**：路由有路径、菜单有项数、层次有深度、缺口有清单。不写"更友好"这类无法验收的话 | 全篇；§11 的验收清单 |
| 5 | IEEE 830-1998 的状态是 **Superseded**，由 ISO/IEC/IEEE 29148:2011 取代（[IEEE SA](https://standards.ieee.org/ieee/830/1222/)，**[已核实]**） | 本项目任何文档**不再写"IEEE 830"** 作为现行标准；引用需求规范时写 29148。（常被引用的"correct/unambiguous/complete…"八项清单原文**未核实**，不逐条断言） | 本节 |
| 6 | **用户故事地图（User Story Mapping）**：顶部是 **backbone**（用户活动），下方挂用户任务；高位的故事描述"能端到端跑通的最小系统"，即 Cockburn 的 **walking skeleton**，Patton 说他"总是先建这个"（[Patton 2008](https://jpattonassociates.com/the-new-backlog/)，**[已核实]**） | 用一张故事地图排**实施顺序**：先让"查一个年号 → 在日历上看到它 → 问助手并跳回该记录"端到端跑通，而不是先把某个库的 12 条 SQL 查询做完美 | §12 的分期 |
| 7 | **心智模型（Mental Model）**：模型基于**信念而非事实**；可用性最大的困境之一是设计者与用户的心智模型之间的落差；同一页出现两个语义不同的搜索框是典型反例（[NN/g](https://www.nngroup.com/articles/mental-models/)，**[已核实]**） | 历法领域有两套模型在打架（线性公历 vs 周期性的年号/干支）。界面必须**常驻显示当前用的是哪套模型**；"查库"与"问助手"不得做成两个长得一样的搜索框 | §5 的状态栏；§6.2 |
| 8 | **C4 模型**：system → container → component → code 四级抽象，notation/tooling 无关，abstraction-first（[c4model.com](https://c4model.com/abstractions)，**[已核实]**） | 本文件的 §4/§5/§6 正好是 container → component → 页面三级；AI 的"数据会离开本机吗"属于**架构级**问题，必须画在 container 图上 | §5、§13 的开放问题 |

### 2.2 心理学：为什么是侧栏、为什么是两级

| # | 依据 | 对本架构的要求 | 落点 |
| - | ---- | -------------- | ---- |
| 1 | **隐藏式导航在桌面端显著更差**：179 名参与者、6 个网站的实测里，桌面端隐藏式菜单的使用率 **27%**、可见导航 **48%**、组合式 **50%**；原文明确"在桌面上隐藏导航对体验与可发现性的损害比手机上更大"（[NN/g](https://www.nngroup.com/articles/hamburger-menus/)，**[已核实]**） | 主导航**常驻可见**（左侧栏），不得收进汉堡按钮 | §5.1 |
| 2 | **扁平 vs 深层**：内容埋在多层之下会降低可发现性，"其它条件相同时，深层级更难用"；层级越深每层类别越少、标签越泛化越难懂；超过几层时用面包屑帮助定位、用站点地图展示整体（[NN/g](https://www.nngroup.com/articles/flat-vs-deep-hierarchy/)，**[已核实]**） | 主菜单**最多 2 层**；"朝代 → 年号 → 年 → 月 → 日"这条天然很深的路径**不做成逐级点击**，改由侧栏直接暴露常用层级 + 面包屑 + 全局跳转 | §4.2、§5.1、§6.1 |
| 3 | **渐进披露存在实际的"两层规则"**：理论上可以有多层，"但在实践中，**超过 2 层披露的设计通常可用性很低，因为用户在层级之间移动时经常迷失**"；确实需要 3 层以上时应"考虑简化设计"，无法简化则"把高级功能**按有意义的组**分块"，并用卡片分类确定分组；另指出"**很少是好主意**去为通往次级选项提供多条路径"（[NN/g](https://www.nngroup.com/articles/progressive-disclosure/)，**[已核实]**） | 这是 §4.2 把"历法 → 8 个体系 → 3 页"压成 2 层的**直接依据**；也是 §6 里"右栏只做一层披露、二级信息走 tooltip 或就地展开"的依据；同时约束模式切换器**只保留一个入口** | §4.2、§5.3、§6.2—6.5 |
| 4 | **Hick 定律**：`RT = a + b·log₂(n)`，选项越多决策越慢；两条落地策略是**分组**（categorizing choice）与**遮蔽复杂度**（obscuring complexity）；原文同时强调这是**指导原则**而非铁律，用户若已预先决定则选项数影响变小（[IxDF](https://ixdf.org/literature/article/hick-s-law-making-the-choice-easier-for-users)、[Laws of UX](https://lawsofux.com/hicks-law/)，**[已核实]**） | 一级项控制在个位数；把 8 个历法与 6 个命理页**分组**而不是平铺；日期输入的模式选择（公历/农历/年号/干支）**记住上次选择 + 显式切换**，不平铺 4 个等价选项 | §4.1、§5.1、§6.3 |
| 5 | **Miller 的 7±2 常被误用**：短时记忆确实只装约 **7 个 chunk**、约 **20 秒**衰减，但 NN/g 明确写道"认为有限的短时记忆意味着**菜单**也该限制到 7 项是常见误解——**长菜单是可以的**……菜单的全部意义就是依赖**再认而非回忆**"；chunking 一文点名"拒绝在全局导航放超过 7 项"就是误用（[NN/g 短时记忆](https://www.nngroup.com/articles/short-term-memory-and-web-usability/)、[NN/g Chunking](https://www.nngroup.com/articles/chunking/)，**[已核实]**） | **不要**为了"凑 7 条"砍导航。一级项数量由"最便于发现"决定（见 [NN/g 导航菜单的三大 IA 问题](https://www.nngroup.com/articles/ia-questions-navigation-menus/)，**[已核实]**），并用分组控制扫描成本 | §5.1 |

## 3. 信息架构

### 3.1 一级分组 = 限界上下文

按 §2.1 第 1 条（限界上下文），22 个分库归并成 **6 个上下文**。归并判据是**用户的问题**，不是**表的前缀**：

| 一级分组 | 用户来这里问什么 | 覆盖的分库 | 为什么这样归 |
| -------- | ---------------- | ---------- | ------------ |
| **工作台** | "这个库现在什么状态、我上次做到哪" | 全部（只读汇总） | 它不是上下文，是**入口与体检**。放在第一位是因为它承担"启动后第一眼"的职责 |
| **助手** | "帮我把这件事做了" | 无（对话与工作流是独立产物） | 助手是**跨上下文的操作者**，不属于任何一个历法上下文。它必须独立成组而不是塞进历法里 |
| **历法** | "某套历法怎么算、某年某月长什么样" | `synodic` `gregory` `jupiter` `natural` `tree` `tropical` `astronomy` + `phase` `phenology` | 这 7 套体系共享**同一个问题形状**（简介 / 日历 / 数据），而月相与节气是**所有历法共用的时间刻度**，不是某一家专属 |
| **年表** | "哪一年发生了什么、谁在位、年号是什么" | `dynasty` `era` `person` `event` `chronology` + `epoch` + `primary` `encounter` `perform` | 这是**历史编年**上下文，术语是朝代/年号/人物/事件；`epoch`（历代建元）与 `primary`/`encounter`/`perform`（元会运世与日月五星行度）在这里是**年表的换算与天象依据**，独立成页会得到 3 行、28 行的空表 |
| **命理** | "按某套术数给我排一个盘" | `part` `week`（+ 历法的换算结果） | 术数用**另一套术语**（四柱、十二宫、躔度），与"查历史"是不同上下文，`week`/`part` 在历法里是刻度、在这里是排盘输入 |
| **数据** | "我要看原始数据本身" | 全部（表格与导出） | 与"历法"分界是：**历法按时间语义组织，数据按表组织**。`/calendar/:system/data` 是"这套历法的历表"，`/data` 是"任意分库任意表的原始视图"——两者面向不同的心智模型（§2.1 第 7 条） |
| **系统** | "为什么慢、谁批准过什么、环境是否就绪" | 无（运行时状态） | 运维上下文。`/system/permission` 对应助手与工作流的授权面（HAX G17 全局控制） |

## 4. 路由

### 4.1 布局路由（无 `component` 的父路由）

按 §2.3 第 17 条，Vue Router 4.1+ 允许父路由不写 `component`，仅用父子关系共享路径前缀、
导航守卫与 `meta`。本设计用**两条**这样的布局路由：

| 布局路由 | 路径 | 承担什么 | 为什么需要 |
| -------- | ---- | -------- | ---------- |
| **主布局** | `/` | 侧栏 + 页头 + 内容区 + 状态栏（`AppShell.vue`） | 现有外壳改造。`meta.chrome: "main"` |
| **沉浸布局** | `/agent/flow/:id` 之下 | 不显示侧栏与页脚，内容区撑满（工作流编辑器画布需要最大面积） | 画布类页面被侧栏切掉 220px 会显著变窄；这条布局让编排器可以全宽 |

> **不写 `component` 的父路由与现有 `DomainOutlet.vue` 的关系**：现有的域文件
> （`view/AgentView.vue`、`view/CalendarView.vue` …）之所以存在，是因为"没有 `component` 的父路由
> 会让子路由无处渲染"——那条经验在 vue-router 5.x（本项目 `package.json` 锁定 `^5.4.0`）下
> **仍然成立**，因为 `DomainOutlet` 提供的正是那个 `<RouterView/>`。本设计不改这一点：
> 域文件继续保留，只是**从 5 个减到 6 个**（多一个 `view/SystemView.vue`，少掉并入的 `YearView`）。

### 4.3 关键路由的设计说明

#### 4.3.1 为什么 `/dashboard` 不写成空路径

现状的概览是外壳的**空路径子页**（`path: ""`），这是被实测逼出来的（见 §1.4 第 1 条）。
新设计**保留**这条实测结论，但把路径显式写成 `/dashboard` 并**同时**保留一个空路径别名：

- 空路径子页的机制不变（`/` 仍然渲染工作台）；
- 但侧栏菜单项需要一个**可点、可高亮、可写进会话记录**的真实路径，`""` 做不到这一点
  （现有 `resolveRoutePath("", "/")` 会返回 `/`，菜单项与"首页"图标因此指向同一个 index）。

> **实现注意**：vue-router 里同时写 `path: ""` 与 `path: "/dashboard"` 两条指向同一组件，
> 会让 `route.matched` 只有一条命中——**但两条路由记录是分开的，`route.path` 分别正确**。
> 若实测发现高亮在两处不一致，改为**只保留 `/dashboard`**，并在布局路由上写
> `redirect: "/dashboard"`。这条需要实现时实测确认，本文件不预设结论。

#### 4.3.2 `/calendar/:system/:view?` —— 把 24 条压成 1 条

```
/calendar/synodic              → /calendar/synodic/entry     （默认子页）
/calendar/synodic/entry        简介
/calendar/synodic/calendar     日历
/calendar/synodic/data         数据
```

- **`system` 的合法值来自一张登记表**（`src/entity/calendar.ts` 的 `CalendarSystems`），
  与 `src/entity/chat.ts` 的 `ChatChannels` 同一个做法：**形状 + 文案 + 图标 + 顺序的唯一来源**。
  路由只做参数匹配，页面对登记表取值。**非法 `system` 走 `ElResult` 空态并给回历法首页的出口**，
  不重定向（重定向会掩盖拼错的地址，与现有 `/:pathMatch(.*)*` 的兜底职责重复）。
- **`meta` 在参数化路由上不能写死标题**。`meta.title` 由页面在 `onMounted` 里写回
  （`route.meta.title = ...` 不是好做法），因此新增 `meta.titleFrom: "system"` 标记：
  `AppHeader` 的当前页胶囊与 `document.title` 从登记表取名字。
  **面包屑同理**：`AppBreadcrumb` 读 `route.matched` 得到的是 `:system`，
  需在组件里对带 `titleFrom` 的节点做一次替换。
- **8 套历法在菜单里只出 4 项**（按 §2.2 第 6 条，按使用频率排）：

  | 菜单项 | 指向 | 为什么 |
  | ------ | ---- | ------ |
  | 朔望历 | `/calendar/synodic` | 唯一有 29 万行真实数据的历法（`calendar.xlsx`） |
  | 格里高利历 | `/calendar/gregory` | 现代通用参照系 |
  | 节气表 | `/calendar/climate` | 1,743,926 行，且是历法判定的核心依据 |
  | 更多历法 | `/calendar/astronomy` | 天文历 / 木星历 / 轩辕历 / 干支历 / 回归历——**当前全部 0 行**，合成一项 |

  > `climate`（节气表）与 `chronology/solar-term`（节气）**是同一个库的两个视图**，
  > 分处两处是**故意的**：前者是"这套历法怎么算节气"（历法语义），后者是"某年的节气在哪一天"（编年语义）。
  > 这符合 §2.1 第 1 条的限界上下文——同一个词在两个上下文里含义不同。**两页必须互相链接**（§10 词表条 6）。

#### 4.3.3 `/agent/chat/:mode?` —— 四模式保留、菜单降为一项

`mode` 的合法值来自 `ChatChannels` 的键，但**去掉 `thought`（思维碰撞）**，见 §6.2 的论证：

| 模式 | 路径 | 菜单 | 说明 |
| ---- | ---- | ---- | ---- |
| 新建对话 | `/agent/chat`、`/agent/chat/create` | 一级「对话」 | 默认。四模式的主力 |
| 深度研究 | `/agent/chat/research` | 对话页内的模式切换器 | 保留 |
| 数据调研 | `/agent/chat/survey` | 同上 | 保留 |
| 课题研究 | `/agent/chat/topic` | 同上 | 保留 |
| ~~思维碰撞~~ | ~~`/agent/chat/thought`~~ | —— | **并入助手抽屉**（见下） |

**思维碰撞（`thought`）为什么从模式降为抽屉动作**：它的形态与其余三个**根本不同**——
其余三个是"用户提任务、助手产出产物（报告 / 数据 / 分析）"，而思维碰撞是"**助手提问、用户产出想法**"。
把它做成一个平级的会话模式，会让"我的产物在哪"这个问题在四个模式上有两种答案。
它更像助手的一个**动作**，因此并入 §5.3 的助手抽屉（"反问我"），
**但 `ChatChannel` 联合类型与 `ChatChannels` 登记表里的 `thought` 条目保留**——
抽屉里的对话仍然是一条 `thought` 会话，仍然出现在会话列表里，只是不再占据一级路径。

> 这一条是本文件里唯一**削减用户明确要求保留项**的地方，因此单独标注：
> 用户要求"保留并优化……（新建对话，深度研究，数据调研，课题研究）"——
> **四个模式一个都没少，路径全部保留**；被调整的只有"思维碰撞"（不在用户列举的四项内）
> 的入口位置。若评审认为它也该保留一级路径，恢复成本是**一行路由 + 一行菜单**。

#### 4.3.4 `/agent/flow/:id` —— 沉浸布局

工作流编辑器需要在 1440 × 720 的默认窗口里给出尽可能大的画布。侧栏 220px + 页头 48px +
状态栏 28px 会吃掉约 300px 宽度与 76px 高度。因此编排器挂在**沉浸布局**下：

- 不渲染侧栏与状态栏；
- 页头瘦身成"返回 + 工作流名 + 保存状态 + 运行 / 中断"（48px 不变）；
- 内部仍是三区：**左栏（节点库）/ 中央画布 / 右栏（属性 / 追踪）**（§7.3）。

#### 4.3.5 兜底与错误态

```
/:pathMatch(.*)*        → redirect "/"          写错的地址回工作台
/calendar/:system 非法  → ElResult 空态 + 出口  **不重定向**（见 4.3.2）
/agent/flow/:id 不存在  → ElResult 空态 + 出口
/agent/report/:id 不存在→ ElResult 空态 + 出口
```

三者一律用 `ElResult`（`globals.d.ts` 已登记），**不用红色告警**——这与现有
`docs/research.md` §3 第 7 条"空态与错误必须分开"是同一条规矩的推广。

### 4.4 `meta` 的扩充

按 §2.3 第 18 条（`route.meta` 是父到子的非递归合并），新增字段只需在**域一级**写一次：

| 字段 | 类型 | 作用 | 写在哪 |
| ---- | ---- | ---- | ------ |
| `title` / `icon` / `description` | 现有 | 菜单文案、图标、提示 | 每条 |
| `menu` | 现有 `false \| "hidden"` | 分组节点与纯出口 | 每条 |
| **`domain`** | `"workspace" \| "tool" \| "calendar" \| "chronology" \| "numerology" \| "system"` | 侧栏分区的归属；**高亮不再依赖 `route.path` 前缀匹配** | 域一级 |
| **`chrome`** | `"main" \| "immersive"` | 是否渲染侧栏与状态栏 | 布局一级 |
| **`titleFrom`** | `"system" \| "flow" \| "report"` | 标题取自参数或数据，而非字面量 | 参数化路由 |
| **`keepAlive`** | `boolean` | 页内切换器要保留滚动与筛选状态（历法工作区、数据浏览） | 需要的那几条 |

`src/globals.d.ts` 的 `RouteMeta` 扩充同步加这四个字段——**新增字段不写这一步，
`vue-tsc` 就拦不住拼写错误**，而"路由表即唯一配置"的安全性正建立在类型检查上。

## 6. 页面层次

### 6.1 工作台（`/dashboard`）

**Tufte 的第一原则**（§2.4 第 6 条）要求先回答"这一页帮用户完成什么思考任务"。
工作台的任务是：**"这个库现在什么状态、我上次做到哪"**。因此它只放四块：

```
1. 库规模（4 张 ElStatistic 卡）
   分库 22 个 · 总行数 11,906,768 · 有数据的库 15 个 · 待生成 7 个
2. 数据健康（一瞥即知，不做实时曲线 —— §2.2 第 12 条警觉递减）
   ElTable：分库 / 行数 / 状态标签（已装数 · 待生成 · 数据源缺失）/ 构建时间 / 备注
   零行的库给"为什么零行"的口径文字（沿用现有 OverviewView 的 note 列）
3. 最近活动（外部记忆 —— §2.1 第 3 条的推论）
   最近会话（3 条）· 最近工作流运行（3 条）· 最近报告（3 条）
4. 继续（前瞻记忆 —— §2.2 第 13 条）
   "上次你在《二十四节气的定气算法》课题停在第 2 环节"，附一个直接跳回去的按钮
```

**明确不做**：不做"控制中心"式的图表墙、不做实时刷新的饼图/环形图
（§2.4 第 4 条：颜色不能编码数量；圆形图表"不能很好地传达定量关系"）、
不做积分 / 连续天数 / 成就徽章（§2.2 第 15 条）。

## 7. 工作流（= Codex 功能）

> **术语约定**：本节把"工作流"按 **Codex 式的编码/执行智能体**来设计——即一个
> **会迭代行动、评估进度、决定下一步**的系统（NN/g 对 AI Agent 的定义：*"a system that pursues a goal
> by iteratively taking actions, evaluating progress, and deciding its own next steps"*，**[已核实]**，
> 并明确"问一个普通聊天机器人、它回答，你用的是 LLM，**不是 agent**"，[来源](https://www.nngroup.com/articles/definition-ai-agent/)）。
> 本节因此同时约束**能力**与**称谓**：只有当一个流程真的会多步执行时，界面才把它叫"工作流"；
> 单轮问答留在对话页。

### 7.1 现状与本设计的差距

现状（`src/state/use-workflow.ts` + `main/workflow.ts` + `shared/workflow-api.ts`，已实读）：

| 已有 | 说明 |
| ---- | ---- |
| 82 个 `dsh-os` 动词清单，**从模块源码静态提取** `arity` 与 `mutating` | `WorkflowVerb` |
| 三步执行：`spawn` 入口脚本 → 解析 UTF-8 JSON 信封 → 流式推事件 | `WorkflowEnvelope` + `WorkflowEvent` |
| 白名单（动词必须在清单里）、形状校验（`isWorkflowStep`）、长度上限（4096 / 24 / 64） | 边界已经很严 |
| 中断、单次运行互斥、UTF-8 三流固定 | `cancelWorkflow`、`activeChild` |
| UI：动作库下拉 + 步骤列表 + 单步参数 + 运行 / 中断 | `FlowStepList.vue` |

**缺什么**（正是"Codex 功能"需要的）：

| # | 缺口 | 后果 |
| -- | ---- | ---- |
| 1 | **工作流没有名字、没有持久化身份**。步骤存在 `localStorage` 的**一个** key（`calendar.workflow.steps.v1`）里 | 只能存在一条流程；换机器就没了；无法版本化 |
| 2 | **只有一条线性步骤序列**。没有分支、没有重试、没有并行 | 表达不了"如果查不到就换个口径再查" |
| 3 | **步骤之间没有数据流**。`args` 是手打的字符串 | 上一步的输出接不到下一步的输入，"工作流"退回成"宏" |
| 4 | **没有意图层**。用户必须在 82 个动词里挑 | 与 Codex 的"说你要什么"相反 |
| 5 | **没有运行记录**。`results` / `streams` 只在内存里 | 跑完就没了，无法回看、无法比对 |
| 6 | **写操作只有布尔 `allow`**，且 UI 上是一个开关 | 与 `dsh-os` 的 `permission.*`（`grant` / `revoke` / `query` / `audit` / `acl.init`）能力不匹配 |
| 7 | **没有产物概念** | 改了哪些文件、生成了什么，界面不说 |
| 8 | **`FlowView.vue` 是 `PageShell` 占位**，`flow/` 下只有 `FlowStepList.vue` | 编排界面基本没做 |

### 7.2 三个页面

```
/agent/flow            定义库：卡片/表格列出全部工作流定义（名称、描述、步骤数、上次运行、版本）
/agent/flow/run        运行记录：一行一次运行（时间、定义、版本、结果、耗时、触发方式）
/agent/flow/:id        编排器（沉浸布局）：左栏节点库 / 中央画布 / 右栏属性与追踪
```

**为什么是三个页面而不是一个带标签页的页面**（§2.3 第 13 条的反向应用）：

| 页面 | 用户此刻的任务 | 频率 | 形态 |
| ---- | -------------- | ---- | ---- |
| 定义库 | "我要跑哪个 / 我要新建" | 高 | 列表 |
| 运行记录 | "刚才那次为什么失败" | 中 | 表格 + 详情抽屉 |
| 编排器 | "我要改这个流程" | 中低，但每次都很长 | 画布 |

三者互相跳转（定义库的每行 → 编排器；编排器的"运行记录"按钮 → 过滤到本次运行的记录）。
**不合并**是因为它三者的滚动方式、宽度需求、停留时长都不同——合并后会得到"标签页里套画布"，
而画布需要全宽（§4.3.4）。

### 7.3 编排器

#### 7.3.1 三区结构（照 Node-RED，§2.3 第 9 条）

```
┌───────────────────────────────────────────────────────────────────────────────┐
```

| 设计 | 依据 |
| ---- | ---- |
| 运行 / 中断在**顶栏**而不是画布上 | §2.3 第 9 条（Node-RED 的 Deploy 在 header；放画布上会与平移缩放冲突） |
| 左右栏**可互换位置** | 同上（Node-RED 的"任何面板都可在左右侧之间移动"） |
| 节点库在左，"多数流程从这里开始" | 同上 |
| 写操作节点打 **⚠写** 标记 | 现状 `FlowStepList.vue` 已有"写"标签，保留并强化 |

#### 7.3.2 节点与连线

采用 React Flow 的词汇（§2.3 第 8 条）：**节点 / 端口（handle）/ 连线（edge）/ 子流程 / 视口 /
小地图 / 缩略控制**。

**连线交互直接照搬 Node-RED 的四条**（§2.3 第 10 条，全部 [已核实]）：

| 交互 | 为什么必须有 |
| ---- | ------------ |
| 拖端口连线 | 基本操作 |
| **按住 `Ctrl` 点端口 → 再点目标** | ①§2.3 第 10 条原文就有这条；②**WCAG 2.5.7 要求拖拽必须有单指针替代**——这一条同时是合规手段 |
| **节点拖到一条线的中点上自动插入（splice）**，插入点显示虚线 | 高频操作：把一步插进已有链条 |
| **`Ctrl+Delete` 删中间节点时自动重连** | 省掉大量手动改线 |
| `Alt` 拖动划过连线批量删除 | 批量清理 |

**连接校验必须即时**（§2.3 第 8 条："把连接校验做成显式规则并在 UI 上反馈，而不是等用户连完再报错"）：

| 规则 | 提示 |
| ---- | ---- |
| 写节点不能直接连到写节点 | "两个写操作之间需要一个确认步骤" |
| `arity` 为 `null` 的动词必须至少 1 个输入 | 在属性面板内联提示 |
| 端口类型不匹配（文本 → 路径） | 连线时端口变红 + 一句为什么 |
| 流程存在环 | 保存时阻止，并高亮环上的节点 |
| 步骤总数 > `WORKFLOW_STEPS_MAX`（64） | 顶栏警告（上限来自 `shared/workflow-api.ts`） |

#### 7.3.3 数据流（缺口 3 的解法）

**这是把"宏"变成"工作流"的关键。** 新增一个**变量层**：

```
变量定义（工作流级）：
  输入参数   name / label / type / required / default
  运行时变量 由步骤产出，按 `{{stepId.field}}` 引用
```

- 步骤的每个参数槽都可以在**字面量**与**引用**之间切换（`ElInput` + 一个 `{}` 按钮）；
- 引用从上游产出里选（下拉列出上游步骤的产物字段，**再认而非回忆** —— §2.2 第 7 条）；
- 运行时的每个变量值可点开看来源步骤（**可追溯** —— HAX **G11**）；
- **型别不符在编排时就报**，不留到运行。

> **与 `shared/workflow-api.ts` 的关系**：现状 `WorkflowStep.args: string[]` 是纯字符串。
> 变量层需要在 `WorkflowStep` 上加一个**可选**的 `bindings?: Record<number, string>`（参数槽 →
> 变量名），**不动 `args` 的形状**——这样旧的持久化数据与 `isWorkflowStep` 校验器都不需要改，
> 变量只在存在时才生效。`main/workflow.ts` 在执行前做一次**解析**（把引用替换成实参），
> 校验仍在主进程（渲染进程送来的东西一律当不可信输入，见该文件注释）。

#### 7.3.4 分支、重试与人类审批

| 能力 | 形态 | 依据 |
| ---- | ---- | ---- |
| **条件** | 节点的一个输出端口名为 `否则` / `若成功`；端口标签可编辑 | Node-RED 的端口标签概念 |
| **重试** | 节点属性里的"失败时重试 N 次 / 间隔"；**上限 3 次**（防滥发） | 现状 `WORKFLOW_*` 的边界风格保持一致 |
| **人类审批** | `mutating` 的步骤可在画布上设为**待批准**：运行到此处挂起，顶栏出现"等待批准"条，展示**将要执行的完整命令行 + 影响**，用户点"允许一次 / 始终允许 / 拒绝" | **HAX G16 传达后果**；**Element Plus 可控性**；并接到 `dsh-os` 的 `permission.grant` / `permission.audit`（§6.7 的 `/system/permission`） |
| **暂停 / 恢复** | 一次运行可暂停，状态落到运行记录，之后从断点继续 | §2.3 第 13 条点出"向导无法优雅中断"，工作流**必须**能 |

#### 7.3.5 子流程（缺口：画布复杂度）

照 Node-RED Subflows（§2.3 第 11 条，[已核实]）：

- 选中一组节点 → **折叠为单一节点**，放进左栏的"子流程库"，可放多个实例；
- 实例属性**参数化**（Node-RED 用环境变量；本项目用上一节的变量层）；
- **状态输出**：实例节点上显示内部当前步骤的状态（Node-RED 的 status 输出）；
- **约束要在 UI 上即时校验**：
  - 子流程**不能包含自身的实例**（直接或间接）；
  - 选区转 subflow 时，**所有流入选区的连线必须连到同一个节点**——因为生成的子流程节点
    **最多一个输入**。不满足时给一句可操作的话（"把三处入口先汇到一个节点，再折叠"），
    而不是只报"无效选择"。

#### 7.3.6 阶段分组

照 Node-RED Groups（§2.3 第 12 条）：

- 节点可结为**阶段组**，整体移动 / 复制；组有边框色、填充色、可选标签；
- **`Ctrl+Shift+C` / `Ctrl+Shift+V` 复制并粘贴"组的样式"到另一组**（样式与分组解耦）；
- 每组自带 **Markdown 说明**，显示在右栏的"追踪"页签下方——相当于每个阶段自带文档。

#### 7.3.7 意图层（缺口 4）

不是"用户在 82 个动词里挑"，而是**两条入口并存**（§2.3 第 16 条：同一功能按熟练度分流）：

| 入口 | 面向 | 形态 |
| ---- | ---- | ---- |
| **模板库** | 新手 / 常见任务 | 定义库页顶部 6–8 张模板卡（"全库行数体检""导出某年历表""重建索引并校验"） |
| **自然语言起草** | 会用但不想画 | 输入一句话 → 助手给出**候选图**，用户在图上看"它打算怎么做"再确认。**必须用户确认后才落成节点**（Element Plus 可控性原则） |
| **手绘** | 熟练 | 就是 §7.3.2 的画布 |
| **命令 / 高级** | 专家 | 顶栏可切到"步骤表"视图（就是现有 `FlowStepList.vue` 的形态），按列 Tab 输入 —— §2.3 第 13 条原文的反例正是"逐条录入向导比按列 Tab 输入更繁琐" |

> **模板与自然语言起草都不可跳过一个动作**：落成节点前**不能自动运行**。
> 这是 §2.3 第 7 条（"给建议可以，不要替用户做决定"）的硬约束。

### 7.4 运行记录与追踪（缺口 5、7）

```
/agent/flow/run                       一行一次运行
└─ 点开 → ElDrawer
   ├─ 时间线：每步的开始 / 结束 / 耗时（横向条形，长度编码时长 —— §2.4 第 4 条）
   ├─ 每步：命令行（可复制）、退出码、信封、stdout / stderr 原文
   ├─ 产物：本次改了哪些文件 / 生成了什么（前后对比）
   └─ 结论：成功 / 失败 / 被中断 / 等待批准
```

**依据**：

| 设计 | 依据 |
| ---- | ---- |
| 耗时用**横向条 + 直接标数值** | §2.4 第 4 条（长度最适合定量表达）；与现有 `docs/research.md` §3 第 13 条"计数用数字直排，不画图"一致 |
| 每步的 stdout / stderr **原文保留** | `main/workflow.ts` 的现有约定（"信封是给程序读的，原文是给人读的，两者都要留"） |
| 运行中**流式输出**，但**先给步骤级状态**再给原文 | §2.3 第 1 条（无结构的长文流式会加剧过载） |
| 中断是**一等按钮**，不藏在菜单里 | **Element Plus 可控性**；WCAG 2.2.2 |
| 状态用**文字 + 图标**，不只颜色 | WCAG **1.4.1** |
| 期待批准时的等待条 `role="status"` | WCAG **4.1.3** |

### 7.5 授权面（缺口 6）

`dsh-os` 已有完整的 `permission.*` 动词（`acl.init` / `audit` / `grant` / `list` / `query` / `revoke`）
与 `selfcheck`。设计把它们**接到界面上**，而不是让 `WorkflowStep.allow` 那个布尔开关承担全部信任：

| 界面 | 行为 | 依据 |
| ---- | ---- | ---- |
| 编排器里的写节点 | 显示 ⚠写 + "需要授权"；属性面板里可预授权（"本次运行允许 `file.create` 写 `docs/` 下"） | **G16** |
| 运行时挂起 | 顶栏出现"等待批准"，展示**完整命令行**与影响范围 | **G16** + Element Plus 可控性 |
| 三个选项 | 允许一次 / 始终允许（写 `permission.json`）/ 拒绝 | 对应 `permission.grant`，与 `os_permission_grant` 的语义一致 |

## 9. 视觉基础

### 9.1 间距

照 Carbon 的标度（§2.4 第 1 条，[已核实]），以 CSS 变量落在 `src/assets/main.css`：

```
--cal-space-01: 2px   --cal-space-05: 16px   --cal-space-09: 48px
--cal-space-02: 4px   --cal-space-06: 24px   --cal-space-10: 64px
--cal-space-03: 8px   --cal-space-07: 32px   --cal-space-11: 80px
--cal-space-04: 12px  --cal-space-08: 40px   --cal-space-12: 96px
```

三条硬规则：

1. **组件内部用 spacing scale，组件之间用 layout spacing**（§2.4 第 1 条）；
2. **应尽量避免偏离标度**；断点处**允许跳级**（如 1440px 用 16、1000px 用 8）；
3. **整页必须有留白**——日历网格可以密，页面不能挤（§2.4 第 1 条原文：
   "Sections of a UI are allowed to be dense, but the whole page should not be crowded"）。

### 9.2 分组：用容器与间距，不用分割线

- **proximity**：检索条件与其结果**相邻**，禁止"筛选器钉在离结果很远的顶部条上"（§2.2 第 9 条）；
- **common region**：区块用 `.xy-panel`（现有工具类）或底色划分；
- **周围空间表达重要性**：当前选中日期、当前历法体系靠**更大的周围空间**突出，不靠更大字号（§2.4 第 1 条）；
- **不用 data-ink ratio 或 chartjunk 这类未核验的术语**做依据（§2.4 第 7 条）。

### 9.3 字体

| 用途 | 字号 | 字重 | 颜色 |
| ---- | ---- | ---- | ---- |
| 页面区块标题 | 16 / 18 | SemiBold（**不用于长文本**） | `--el-text-color-primary` |
| 正文 | 14 / 16 | Regular | `--el-text-color-regular`（**中性色**） |
| 说明 / 口径 | 13 | Regular | `--el-text-color-secondary` |
| 计数 / 时间戳 | 12 | Regular | `--el-text-color-placeholder` |
| 历表数字 | 12 / 13 | Regular | `var(--el-font-family-mono)` + `.numeral`（现有） |

依据：§2.4 第 2 条（Carbon **productive** 字型集：更紧凑以维持任务专注；
**SemiBold 只用于区块标题**；**正文保持中性色**；**主操作用主色，不用颜色装饰**）。

### 9.4 尺寸与交互硬指标（WCAG 2.2，§2.4 第 3 条）

| 指标 | 值 | 落点 |
| ---- | -- | ---- |
| 指针目标 | ≥ **24 × 24 CSS px**（含例外：间距足够的可豁免） | 日历格、图节点端口、状态栏按钮、表格行内按钮 |
| 正文对比 | ≥ **4.5:1**；大号文本 ≥ **3:1**（中文按 CJK 等价字号） | 全部文本 |
| 非文本对比 | ≥ **3:1**，**计算值不四舍五入**；避免过细线条 | 图标、边框、状态指示、连线 |
| 焦点外观 | 可见焦点环；§2.4 第 3 条的 2.4.13 给了 AAA 级算式（≥2px 周长面积、3:1），本项目**按 AA 起步但用 AAA 的算式自检** | 所有自绘按钮与画布节点 |
| 焦点不被遮挡 | 侧栏、状态栏、悬浮工具条**不得完全遮住**获得焦点的元素 | 固定的状态栏 28px 与顶栏 48px 要留出 tab 顺序 |
| 拖拽替代 | **所有拖拽都有单指针替代** | 图连线、日历拖拽改期、表格拖列、面板拖宽 |
| 状态消息 | `role="status"` / `aria-live="polite"`，**不抢焦点** | 助手状态行、工作流运行状态、自检依据 |
| 缩放 | 文本可放大到 **200%** 不丢内容 | 全局 |

**明确不做**：不用"AI 可能出错"的小标签代替核查动作（§2.3 第 3 条原文点名了纯文本框的这个缺陷）；
不用"仅供参考"这类模糊免责语（§2.3 第 2 条原文点名了 DeepSeek 的写法）。

### 9.5 AI 标记（本项目自建，照 Carbon for AI 四原则）

Element Plus 没有 AI 标记体系（§2.4 第 9 条），因此本项目自建一个组件与一套样式变量，
**只消费 `--el-*`，不新增硬编码色值**（沿用 `src/assets/main.css` 的现有做法）：

| 元素 | 行为 | 依据 |
| ---- | ---- | ---- |
| **AI 标记**（`<AiBadge>`） | 出现在任何 AI 生成的内容上：助手回答、AI 摘要块、被助手填入的字段、报告的 AI 段落 | §2.3 第 6 条原则 ①"标记任何 AI 使用实例" |
| 点标记 | 弹出**摘要级**解释（依据了哪几个库、用了哪个口径、局限是什么） | 原则 ③"先给摘要级说明" |
| **AI 变体字段** | 助手填进表单的值呈 AI 变体样式；**用户一改就恢复默认样式**，并保留「恢复助手建议」按钮 | 原则 ④ 的 Revert 语义 |
| **不做装饰** | AI 样式只用于标识 AI，不用来美化 | 原则 ④原文 |
